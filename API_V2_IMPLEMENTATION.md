# 0.0.1 implementation status

This describes working-tree code, not the currently installed service or a released SDK. The full target contract remains in [API_DESIGN.md](API_DESIGN.md). The beta is not yet release-ready. The user confirmed this is a fresh 0.0.1 release with no backward compatibility requirement: there is one API under `/api`, with API version `0.0.1`. Prototype routes and token-derived authentication have been removed. Some internal class/file names still contain `V2` and will be cleaned up with the remaining prototype code.

## Available HTTP operations

The SDK's `connect(options?)`, `config(...).connect()` and `search().connect()` return a connected print library. Use `await print.getPrinters()` to retrieve installed queues, then `print.target(name)` to render/print. Returned libraries retain their service binding across later top-level selections; `print.connection` provides copied server metadata without printers. The HTTP handshake still validates inventory internally. Bundle the SDK directory with the client application; Entree POS is one client of this standalone product. Nine real service-contract scenarios exercise the current SDK.

| Route | Current behavior |
| --- | --- |
| `GET /api/health` | Public service/boot identity, protocol/version and cached readiness; optional echoed `requestId` |
| `GET /api/heartbeat?requestId=...` | Authorized, uncached echo/identity; does not query printers or create jobs |
| `GET /api/connection` | Authorized inventory refresh; distinguishes no printers from query failure |
| `GET /api/events/checkpoint` | Authorized complete cached printer snapshot and service cursor, locked against partial inventory publication; pending job events are flushed first |
| `GET /api/events` | Authorized SSE: ready, ordered job/printer replay, caught-up, live updates and heartbeat; cursor in query or Last-Event-ID header; explicit expired-history errors |
| `GET /api/printers?refresh=true` | Installed queues, driver-owned settings source, optional device helpers and timestamped status observations |
| `GET /api/printers/status?printer={encodedName}&refresh=true` | Status for the selected queue; query encoding preserves special characters |
| `POST /api/renders` | HTML or ordered HTML/QR/barcode blocks into saved positioned layout and display-ready HTML |
| `POST /api/jobs` | Print a saved render, or a profiled `beep`, `open_cash_drawer`, `cut`, `send_command` operation |
| `GET /api/jobs` | `{ items, nextCursor }`; printer, station, orderID, repeated status and since filters; default 30, maximum 100 |
| `POST /api/jobs/{id}/reprints` | Explicit linked copy using a new idempotency key and the original retained receipt |
| `GET /api/jobs/{id}` | Versioned job, original acceptance digest and Windows delivery evidence |
| `GET /api/jobs/lookup?idempotencyKey={encodedKey}` | Same job view using its exact persisted POS key; authorized, uncached and service-identity checked |
| `GET /api/jobs/{id}/render` | The accepted layout's HTML preview; never re-renders the current order |

The fluent SDK is in [sdk/entree-print.mjs](sdk/entree-print.mjs), with usage and current limits in [sdk/README.md](sdk/README.md). It supports configuration/connection, immutable targets/tickets, prepared HTML, print/device jobs, exact-byte retry and acknowledgement checks, paged history, explicit reprints, local connection heartbeat/resume events, awaitable native discovery and same-service address recovery. `connect(options)` accepts settings directly or a discovered server record, verifying a supplied service ID. Ordered initial selection through `connect({ nodes, failover, timeoutMs })` now chooses one verified server and returns its bound library; it does not transfer existing tickets. Backup selection restricts receipt output to identified network queues and requires explicit owner connections for device commands/reprints, including outbox submission. Resumable job/printer events and ordered `after` actions are implemented; automatic routing during printing remains pending. The confirmed topology is USB cashier receipts and Ethernet regular printers; backup selection keeps USB operations pinned; Windows queues on eligible nodes must be configured for the intended Ethernet printer, without plugin printer profiles. Prototype routes are not mapped. Bundle the SDK with the POS; the service does not deliver executable JavaScript or embed a token in it.

History filters apply before pagination, ordered by acceptance time and job ID descending. Opaque cursors bind to service identity and filters; page size can change. Status filters are live, not a frozen snapshot. Reprints retain the original receipt, destination and metadata, link `reprintOf`, reject active originals/device commands, and recheck the original driver geometry fingerprint. Acceptance rechecks eligibility and content atomically. Replaying an already accepted reprint key does not depend on current preview expiry or printer availability. POS must explain uncertainty before an operator reprints a `needs_attention` job.

`print.getJob({ idempotencyKey: savedIntent.id })` recovers an accepted job when POS lost its returned ID. Persist the key and owning `serviceId` before submission, and reconnect with that identity. Lookup does not query the printer, render or submit; it works after layout compaction and service restart. Keys are exact/case-sensitive, 1–200 characters and not all whitespace. Missing/duplicate/invalid query values fail validation. `JOB_NOT_FOUND` is a 404 snapshot, not proof that an earlier request was never accepted or is no longer in flight. The SDK marks lookup failures `delivery: 'unknown'` and never automatically creates another job or changes its owner. Unsent work and durable POS outbox integration remain pending.

Confirmed printer conditions (offline, paper-out, cover-open, paused) keep accepted receipt jobs waiting without exhausting the backend retry limit. The original layout and key remain on disk. Repeated unchanged observations do not advance the job version or rewrite its file. Six queue tests cover printer independence, four blocking conditions, restart recovery, return to service, stale observations and no repeat of the already completed destination. This uses fake printer inventory/output and real disk storage; physical fault pilots remain pending. A stale or missing observation lets Windows handle the job instead of treating old sensor data as current. Possible handoff is never retried automatically.

Status collection now uses Windows inventory exclusively. The global ESC/POS network probe, its timeout/enable settings and raw probe detail field were removed. This follows the user's driver-ownership decision and avoids sending unsolicited printer-language commands during polling. Query stdout/stderr use explicit UTF-8; real child-process fixtures verify Chinese queue names and query errors. A development-user read-only inventory refresh returned seven queues, all with `source: windows`, including one Windows-reported offline queue. This does not establish physical sensor accuracy or service-account permissions.

## Ordered receipt actions

`print({ after: { beep: true, cut: true } })` is now implemented in the HTTP API, fluent SDK and optional client outbox. Validation captures supported command bytes at acceptance; receipt, optional cut and optional beep retain one job/key and queue position. A raw cut requires an explicit `CutMode: "raw"`; the default remains Windows driver cutting. Every phase retains its own Windows submission identity, observations and handoff uncertainty in the parent's atomic record. Public `job.after` exposes individual phase outcomes; history filters and overall state account for action failures. Job events capture the complete phase snapshot at that version.

Restart resumes only known-unsent trailing work, never the receipt or an ambiguous action. Later actions are skipped after failure/uncertainty. Phase-state storage failures keep the per-printer queue position, and receipt retention waits for final action completion. Explicit reprints preserve original actions and reject active Windows phases. No automatic raw action retry is introduced.

All **370 .NET tests and 95 core SDK tests** pass locally. Nineteen action cases cover queue order, typed/ambiguous failures, phase IDs, replay, restart windows, snapshot copying, storage barriers, retention and validation; a ninth actual SDK/TestServer scenario uses real Chromium, loses both ACKs, reopens storage and recovers one receipt/cut/beep sequence with no duplicate delivery. Two added SDK cases cover immutable flags and outbox wire recovery. This does not prove physical beep/cut behavior or real machine power-loss recovery; those remain pilot work.

## Client outbox

Submission evidence now survives later rejections. The SDK combines all automatic attempts and retains possible acceptance per ticket intent across repeated calls; only a genuinely unsent intent can replace an expired preview. The client outbox commits possible acceptance before every POST and preserves it across lost ACKs, failed local ACK saves, explicit retries and store/SDK reopen. Later non-acceptance of a retry cannot prove earlier non-acceptance. This fixes a prerequisite for safe node routing; shared cross-client ownership and automatic printing failover are still unimplemented.

The optional client-side `EntreePrint.outbox()` adds `enqueue`, `list`, `flush(print)`, `retry`, `cancel` and `stopRetrying`. It stores source content before network work, commits exact request bytes before submitting and preserves possible delivery after lost ACKs or local ACK-save failures. The default IndexedDB/Web Locks implementation coordinates tabs per destination and requires the client to invoke flush after reconnect/startup. It never transfers ownership to another service. The full contract, states and limits are in [sdk/README.md](sdk/README.md#durable-client-outbox). This is client storage, separate from the service's accepted-job ledger. Native Node/Electron main clients can now use the optional SQLite adapter, which commits intent data separately from per-printer OS-backed dispatch locks. Process-exit, cross-process deduplication and lost-ACK recovery tests pass; a seventh SDK/TestServer scenario verifies the production adapter with real Chromium preparation and reopened service storage. Business routing, cross-device claims and automatic local pruning remain unimplemented.

### Durable events and SDK recovery

The service now exposes the durable history through authenticated SSE. Initial cursor validation happens before the streaming response. Public job payloads are mapped from the saved version, without replacing old replay with the current job. Printer events capture public status fields and queue removal tombstones. A checkpoint captures the complete cached printer inventory and event position under the inventory-publication lock; partial publication failures reject checkpoints until the next successful refresh.

The SDK shares a stream between equivalent verified sessions, carries the bearer token in a header, resumes the last acknowledged cursor, checks service/sequence/version identity and reconnects with bounded backoff and a silence timeout. On initial subscription or history expiry it reads a printer checkpoint, pages unfiltered jobs and replays from the earlier cursor with job-version deduplication. Synchronization phases distinguish snapshot/replay/caught-up from service heartbeat reachability. This is convergent reconciliation, not a frozen multi-page job snapshot. New subscribers receive a shared snapshot refresh. Closing the last remote subscriber releases the stream. See the [SDK contract](sdk/README.md#resumable-status-updates) for lifecycle/snapshot payloads and consumer responsibilities.

The original durable storage foundation and its earlier verification follow for context. Public SSE and SDK reconciliation are now implemented; live LAN/OS recovery remains unverified.

Current local verification: all 350 .NET tests, 93 core SDK tests, eight playground tests and 22 package checks pass. Fifteen SSE/API cases cover authorization, immutable replay, restart cursors, invalid/foreign/expired positions, disconnect cleanup, queue removal and failed inventory publication. Twelve SDK cases cover recovery, shared streams, timeout, sequence gaps, snapshot races and fragmented UTF-8/SSE. The eighth production SDK/TestServer scenario forwards actual SSE bytes and reopens storage; it observes versions 1/2/3 with zero render or submission calls.

The service now stores bounded event history under `spool/events`: at most 2,000 events and 16 MB, using a flushed atomic replacement, a verified state digest and a single-writer file lock. Sequence IDs survive reopening. Internal replay reads reject future/invalid and pruned cursors; missing/corrupt history is not reset. Job event payloads capture the job version and immutable request metadata, without prepared receipt geometry. Printer observations can also be recorded by the broadcaster. The authenticated SSE route and SDK recovery now use this history.

Each new job state atomically retains pending notification snapshots in the same job document. Publishing to event history and clearing that pending list can be retried independently. Event-history failure does not falsely reject a durably accepted job or erase intermediate states. A job can retain up to 256 pending notifications; further changes fail without discarding that backlog. Startup, later job writes and the minute-based maintenance worker retry publication. Replay may repeat an entity version after a crash/pruning, so consumers must deduplicate versions. A full live subscriber channel now ends with an explicit gap error rather than dropping older updates silently.

Fourteen new cases cover durable replay, bounded history, unchanged/invalid versions, failed writes, missing/corrupt files, single-writer ownership, subscriber overflow, pending acceptance, multiple retained versions, publication/clear crash windows, backlog capacity and real API job transitions across store reopen. API and SDK/TestServer tests now use this durable broadcaster. One full-suite run produced a transient renderer 503; its isolated rerun and the following full run passed. The test harness now captures API exception details for recurrence; no renderer fix or explanation is claimed from that non-reproduction.

Ordered connection selection is covered by 15 additional simulated SDK cases: unavailable/silent/wrong-identity/empty primary, credential isolation, bounded cancellation, concurrent selection, lost-ACK owner retention, backup USB/device/reprint restrictions, and outbox preparation/saved-wire checks. All 81 SDK tests, eight playground tests and six existing real SDK-to-TestServer scenarios pass after this change. These do not exercise live backup servers or establish physical printer equivalence.

## Authorization and request integrity

Configure the token in the tray's **Security → API access token** field using **Generate token**, then Save and restart the service. The tray generates 32 random bytes represented as 64 hex characters; the value is masked until **Show token** is selected. **Replace token** stages a replacement in the form; it takes effect only after Save and service restart, and every POS must then use the replacement. Reset Default preserves existing credentials and printer profiles. This UI is in source and has been visually checked in an isolated preview; the installed tray/service has not been updated with this change.

Administrators can also configure `AccessToken` in the service JSON or `ENTREE_PRINT_API_TOKEN` in its environment. It must be a random token of at least 32 characters. Except for `/api/health`, requests require `Authorization: Bearer <token>`; an unconfigured token fails with `AUTH_NOT_CONFIGURED`. Secret phrase, salt and derived-token settings are removed. There are no aliases or conversion paths for prototype credentials.

**POS website address** is the browser CORS origin list: scheme, host and port, without a page path. The client-facing screen describes it as the address used to open the POS, with an example showing which part to enter. Comma-separated origins are supported; `*` allows all origins and blank allows no cross-origin browser access. Invalid paths, credentials, query strings, fragments and mixed wildcards are rejected. An allowed origin still needs a valid token. CORS does not restrict native clients or replace authentication.

Configuration precedence is the named deployment override (for example `CORS_ALLOWED_ORIGINS` or `HTTP_PORT`), then flat tray settings, then bundled `Plugin:*` defaults. This fixes the previous behavior where bundled defaults could silently override saved website rules, ports and other preferences. Explicit environment token overrides still take precedence over the tray field.

POST requests also require:

- `Content-Type: application/json` with uncompressed UTF-8 bytes.
- `X-Entree-Content-SHA256`: SHA-256 over those exact bytes.
- `X-Entree-Service-ID`: the identity returned by the selected service's connection handshake.

Successful mutations echo the current request digest in `X-Entree-Content-SHA256`. The stored Job retains the digest from its original acceptance. Same meaning with different JSON whitespace can replay the existing job; changed receipt/profile/destination/metadata/command data conflicts. Unknown service identity, invalid authentication/digest/schema and oversized requests produce no new job. The one-megabyte request limit applies while reading chunked bodies as well as to Content-Length.

The Windows service defaults to HTTP and supports HTTPS using `HttpsCertificateThumbprint` and `HttpsHost`, with a private-key certificate in Local Computer / Personal. Invalid configuration/certificate stops startup without HTTP fallback; the configured port has one listener. See [setup and deployment limits](BETA_SETUP.md#https-setup). Discovery advertises the scheme and verifies actual sender IPs; HTTPS searches/recovery reject HTTP announcements. Connection monitors include protocol in their ownership boundary. The 386 .NET and 98 core SDK tests include encrypted Kestrel memory-transport requests, wrong-host/untrusted-issuer rejection and transport isolation. These tests do not prove installed private-key access, trusted tablet certificates or live LAN recovery. A checksum is not authentication or encryption. The browser SDK requires Web Crypto (normally a secure context); Electron/Node can supply its native Web Crypto implementation.

## Windows printer settings and optional commands

Normal receipts use Windows printer settings. The optional service-only `PrinterProfiles` map is keyed by Windows queue name and contains device-helper fields only: `CutMode`, `BeepCommandHex`, `DrawerCommandHex`, `CutCommandHex`, `AllowRawCommands`. Paper width and DPI fields have been removed; there is no customer profile editor.

The user rejected duplicate plugin printer configuration. Paper size, printable area, DPI and driver-supported cutting are owned by Windows. The profile editor was removed. `render()` reads current driver measurement graphics, using the actual printable width and DPI without requiring a profile or `widthMm`. An optional `widthMm` narrows content and cannot exceed the driver area. QR/barcodes use the driver resolution; the current code renderer requires equal horizontal/vertical DPI. The current receipt renderer still supports widths of 20–100 mm. A driver reporting a wider page requires a narrower explicit content width; broader page support remains outside current receipt coverage.

Driver reads create no print job and have an eight-second response deadline, with at most two native queries in flight. Unavailable settings return `PRINTER_SETTINGS_UNAVAILABLE`; the service does not guess a receipt profile. A preview freezes a geometry/driver fingerprint. New acceptance and reprints recheck it and report `PRINTER_SETTINGS_CHANGED` when it changes. Lost-ACK replay of an already accepted job still returns its original record. Standalone device-command helpers remain optional and require verified bytes; custom raw bytes require `AllowRawCommands`. Ordinary printing does not require those helpers or customer command setup.

The backend draws the accepted layout without running Chromium again and preserves the driver's default paper. Before StartDoc it plans every page using the printable width/height. Text keeps its original size; lines and `break-inside: avoid` sections stay whole. QR/barcode blocks, including optional labels and quiet zones, are automatically kept together. Oversize indivisible content returns `LAYOUT_ITEM_TOO_TALL` before submission; width overflow or more than 256 pages returns `LAYOUT_OVERFLOW`. Backgrounds/borders are clipped to each page. Empty trailing pages caused by bottom padding are omitted. All pages use one tracked Windows job; a later-page failure remains uncertain and is not retried automatically. The POS HTML preview remains the continuous saved receipt; a paged preview UI is not implemented.

Microsoft Print to PDF job 20 verified the current default-page path with a 120-item receipt across four Letter pages at 600 DPI, completed with flags 388. All four rendered pages were inspected; their item ranges are 001–034, 035–074, 075–114 and 115–120, with intact Chinese text and codes. Both codes decoded from the final PDF page rasterized at 300 DPI. The driver rasterized 16 individual text bands at its full 600 DPI, so the PDF is not entirely searchable/vector text; 109 of 120 items are extractable. No whole-receipt screenshot was submitted. Barcode sizing now keeps minimum physical bar width around 0.25 mm, with preferred widths near 0.375 mm, using whole device dots. Thermal feed/cut behavior, physical scanner validation, service-account settings remain release gates.

## Storage and verification

Windows recovery now includes persisted submission attempts whose numeric Windows job ID was never saved. A bounded `EnumJobsW` snapshot can bind exactly one matching unique document name in the same queue. Missing, ambiguous and mismatched results remain uncertain and are never resubmitted automatically. Existing IDs are not rebound. Uncertain full handoff remains `needs_attention` even if Windows later reports completion; while Windows reports the job active, its `spooler.state` reflects that activity and explicit reprinting is refused. Active evidence survives a late worker failure. Unresolved Windows ownership remains monitored beyond one day.

Thirteen new disk-backed tests cover this behavior, bringing the .NET suite to 217 passing tests. A native .NET 10 audit found Microsoft Print to PDF job 22 after deliberately omitting its numeric ID and reopening the ledger. It retained uncertain handoff, blocked an active reprint and was aborted/removed before page drawing or EndDoc. No receipt/PDF was produced. This is an API/ledger reopen test at the handoff boundary, not an actual Windows service/process kill or physical-printer pilot.

The actual JavaScript SDK now has three integrated scenarios against the production ASP.NET handlers through an in-memory stdio fetch bridge. These use real Chromium preparation and the durable ledger/processor with simulated driver inventory and delivery. Lost acknowledgements, invalid acknowledgement digests, exact-byte corruption, Chinese/slash queue names, metadata/history, explicit reprints, preview retention after store reopen, and independent offline destination recovery pass. The integrated status call exposed encoded-slash loss in the former path route; the current status endpoint carries the printer name in a query parameter. Total current checks: 204 .NET and 42 SDK tests. See `sdk/integration/README.md` for scope and execution. Live network, Windows-service restart and physical printing remain separate gates; older counts below describe earlier evidence.

Generated code rectangles retain their integer module geometry and driver DPI. The extractor snaps the shared code origin once, preserving every encoded bar width despite Chromium's subpixel quantization. The saved layout and preview use those aligned edges. Pagination selects boundaries on the same printer-dot grid, protects code rectangles as well as their keep-together regions, and rejects a mismatched code DPI before StartDoc. Plain text and ordinary graphics keep their original coordinates. The document root now uses the exact fractional receipt width, fixing right-aligned content that previously targeted Chromium's rounded-up viewport.

Eight additional tests cover real Chromium fractional positioning at 203/300/600 DPI, unchanged module dimensions after extraction, preservation through page breaks, unaffected text/ordinary graphics and resolution mismatch rejection. Current-path Microsoft PDF job 21 completed as one four-page job (flags 388); all 120 items were inspected across the four rendered pages, and both codes decoded from the final page at 300 DPI. Artifacts are in `output/pdf/long-receipt-dot-aligned`. As with job 20, 16 driver-generated text bands remain at native 600 DPI; this is not a fully vector/searchable PDF guarantee.

The production backend accepts saved positioned receipts and explicit device commands only. It no longer renders HTML during delivery, selects a default printer, writes duplicate preview artifacts, or falls back to screenshot/PDF/native ESC/POS receipt output. The historical screenshot and image printer code now lives only in `samples/PrintComparison`; unused prototype block and ESC/POS receipt renderers and their settings were removed. Current verification includes eight backend rejection cases, real UTF-8 query fixtures, twelve pagination cases and two additional 600-DPI barcode cases, within the full 181-test suite.

Unused previews expire after 30 minutes and are cleaned when preparing more previews. Preparation is limited to two concurrent renders, 1,000 stored previews and approximately 256 MB of preview files (each at most 8 MB). Accepted layouts are copied into the flushed atomic job record; expired preview files cannot break accepted-job replay/history.

Finished receipt layouts become eligible for compaction seven days after completion by default. Set service-only `ReceiptRetentionDays` (1–365), or `RECEIPT_RETENTION_DAYS`, before starting the service. Pending, Windows-active and delivery-uncertain receipts do not expire. The cleanup worker runs at startup and each minute, processing at most 100 records per pass and releasing the ledger lock between files. An expiry already recorded on a finished job is preserved when configuration changes; new completions use the new policy. Jobs expose `artifactExpiresAt` and `artifactExpiredAt`; the connection exposes `retention`.

Compaction atomically replaces only the saved layout with its content hash, retaining the command identity, original request digest, metadata, job state and Windows evidence. The original exact request bytes return the same job after compaction/restart, without querying a printer or loading a preview. Changed bytes for a compacted intent receive `IDEMPOTENCY_CONFLICT`. Expired previews/reprints return `ARTIFACT_EXPIRED`; existing reprint acknowledgements remain replayable. Stored intent records do not expire or get silently evicted: retry protection lasts for the retained ledger's lifetime.

Admission stops at 100,000 total intent records, 10,000 records with prepared layouts, or a 512,000,000-byte ledger acceptance budget. Cleanup frees layout count/bytes, but does not free intent IDs. Existing jobs and duplicate acknowledgements still work when new acceptance returns `QUEUE_FULL`. Status updates for accepted jobs may grow the ledger beyond the admission byte budget; this is not a hard filesystem quota. Preview files have their separate budget. Operators must retain service identity and the ledger together; automatic long-term history removal/export is not implemented.

181 .NET tests and 42 Node SDK tests pass. Three obsolete derived-token/SDK tests were removed; seven new cases verify prototype routes are absent, and processor reliability tests now use the current validated-command entry point. Endpoint tests exercise the actual filters and handlers through ASP.NET's in-memory TestServer with fake inventory/delivery, plus a real Chromium Unicode preview. They cover exact-byte corruption, malformed digests/UTF-8/JSON, duplicate keys, truncated/oversized uploads, authorization/identity mismatch, empty/failed inventory, concurrent duplicate acceptance, changed metadata, retained artifact integrity, expired new previews and lost-ACK replay. SDK tests use a fake HTTP boundary, real Web Crypto and controlled timers to check snapshots, generated keys, retained bytes after lost/invalid ACKs, explicit expired-preview handling, helpers, cancellation, heartbeat non-overlap and rejection of reused-address identity changes. Full SDK-to-service/network/Windows/hardware integration remains pending.

## Discovery implementation evidence

The native SDK entry point is `sdk/native.mjs`; the browser entry point requires an injected discovery transport or manual configuration. IPv4 UDP scanning is bounded to one round/64 endpoints, uses datagram source addresses, and verifies fresh public HTTP health nonces before authorized connection. Search builders share collection; `.connect()` resolves at the first successful handshake and cannot overwrite a newer selection. Recovery keeps the selected service ID and prepared ticket, uses capped jittered backoff, and never submits a receipt. Browser lifecycle and optional Electron powerMonitor resume hooks mark observations stale and refresh the inventory. The service's UDP listener now respects its configured bind address, including localhost-only mode.

The 42 SDK tests include simulated socket cleanup/failures, search timing, duplicate endpoints, auth failures, stale/mismatched identities, cancellation, candidate floods, address recovery and resume handling. Six additional cases cover reused configurations, shared alias monitoring, policy/credential isolation, concurrent polls, stale handshake ordering and one recovery scan updating multiple prepared-ticket sessions without submitting jobs. Identical configurations reuse a session; equivalent verified service identities share one heartbeat/recovery monitor within an SDK client. A monitor's token, request deadline and heartbeat policy must match. Each connection caller receives an independent result copy. Older handshakes cannot undo newer verified addresses. Disconnect clears monitor registrations and timers. This is same-server address recovery, not cross-node failover. No real LAN UDP discovery or OS sleep/resume was exercised; durable event/job reconciliation and full transport integration remain release gates.
